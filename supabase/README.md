# BPJ Supabase setup

Target project: `benbawoavrvipdyuzffw`. These files have **not** been applied or deployed remotely. The migration creates new BPJ tables; it does not drop existing application data. Apply once; if conflicting BPJ tables already exist, inspect and reconcile rather than dropping them.

## Apply in order

1. Back up existing data. In Dashboard SQL Editor apply `migrations/202611170001_bpj.sql` (or use your normal reviewed migration process).
2. In Dashboard Authentication create/invite the first administrator with a strong password. Disable public Auth signups. Set Site URL and explicit redirect URLs to your real frontend origins. Configure SMTP before relying on password reset.
3. Replace the placeholder email in `bootstrap_admin.sql` with that existing Auth user's email and run it. No password is embedded in SQL. Authority lives in `staff_roles`, not editable Auth metadata. An Auth user alone has no staff access.
4. Add verified letter types and real signatories. There are deliberately no fabricated officials or production applicant records. As admin call `bpj_staff_action('saveLetterType', '{"code":"...","name":"...","requirements":[],"active":true}')` and `manageOfficial` with `{name,nip,role,active}`. Or insert verified records using Dashboard SQL. Existing submissions keep their type relation; removeLetterType deactivates rather than deletes.
5. Set Edge secrets with your trusted Supabase CLI / Dashboard: `BPJ_ALLOWED_ORIGINS=https://your-production-host` (comma-separated exact origins, no wildcard), `BPJ_RATE_LIMIT_SALT` (random secret at least 32 characters). Supabase provides `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` to deployed Edge functions. Never put the service-role key in frontend env, logs, or Git.
6. Deploy with `supabase functions deploy bpj-guest --project-ref benbawoavrvipdyuzffw --no-verify-jwt`. The guest gateway deliberately accepts unauthenticated callers; it does not grant guest database access.
7. Frontend only: `VITE_SUPABASE_URL=https://benbawoavrvipdyuzffw.supabase.co`, `VITE_SUPABASE_PUBLISHABLE_KEY=<Dashboard publishable key>`, `VITE_APP_MODE=live`. Copy the root `.env.example` to `.env.local` if it is absent, keep these public values, and restart `npm run dev` (or rebuild/redeploy the frontend). The supplied workspace already has an ignored `.env.local`; deployment environment variables must be configured separately. Demo must be explicit (`VITE_APP_MODE=demo`), never a production fallback.
8. Verify production gateway proxy behavior **before opening traffic**. The handler uses the rightmost `x-forwarded-for` hop and fails closed when absent/malformed. Confirm Supabase's deployed gateway appends/overwrites this value with the trusted client peer, and that arbitrary client-supplied forwarding headers cannot change the selected peer. Only after this verification set `BPJ_TRUST_PROXY_MODE=supabase-append-rightmost-verified`; without this explicit attestation the entire gateway returns 503. If this guarantee is unavailable, keep the function disabled and integrate a documented trusted ingress rate limiter; do not trust an arbitrary request header. CORS is a browser boundary, not authentication or anti-abuse protection.

## API contract

All guest calls are POST JSON to `/functions/v1/bpj-guest` with `{action,payload}` and an allowed browser Origin. Responses are `{success:true,data}` or `{success:false,message}`. Do not put NIK/tracking codes in URLs or analytics. Bodies are capped at 80 KiB and validated server-side; tracking uses an indistinguishable not-found response.

- `submit`: `{letter_type_id,nik,nama,email?,phone?,form_data:{alamat,keperluan,instansi?,keterangan?},attachment_tokens?:string[]}`. Email is optional. Active type, 16-digit NIK, name, address, purpose and optional email are checked on the server. Returns `{id,tracking_code,status,created_at}`. Save the 128-bit random tracking code; it is not recoverable through public APIs.
- `track`: `{nik,tracking_code}` returns only status/type/timestamps/official number/rejection reason. Never applicant name, NIK, full form, staff notes or documents.
- `upload`: `{content_type,size}` allows PDF/JPEG/PNG up to 10 MiB. Returns `{token,path,signed_url,upload_token,expires_at}`. Use the Storage SDK `uploadToSignedUrl(path, upload_token, file, {contentType:file.type})`, then pass the database capability `token` to submit. Paths are server-generated. Max five files. Signed URLs use `upsert:false`; finalization locks and consumes each capability, verifies object size/type/path, and binds it to the new submission atomically. Never reuse the storage SDK's separate signed-URL token as the database token.
- `remove`: `{token}` cancels an unconsumed capability. It intentionally does **not** delete the object immediately: a previously issued storage signed URL remains valid until the provider expiry. An expired/cancelled capability cannot attach a file to a submission.

Auth session: `bpj_my_profile()` returns merged own profile with role and is_active, or null. Staff role values are `super_admin`, `verifikator`, `petugas`. Raw staff_roles has no client grants or policies. `bpj_staff_action(p_action,p_payload)` returns `{success:true,data}`. Actions: getSubmissionById, getAllSubmissions, updateStatus, verifyAndComplete, createWalkInSubmission, generateLetterNumber, validateLetterNumber, saveLetterType, removeLetterType, manageOfficial, manageStaff. Walk-in uses the same normalized submit payload plus optional status/nomorSurat/pejabatTTD/catatanVerifikasi. Verifiers/admin issue/reject; only admin manages types, officials and staff. `manageStaff` requires an already-created Auth user id; cannot change one's own authority. Petugas can intake/read but not approve. `generateLetterNumber` reserves a monotonic per-year sequence (gaps are intentional); completion is the authoritative atomic uniqueness check. `validateLetterNumber` is advisory only. Completion accepts a verified official UUID or exact active official name.

Staff may SELECT submissions/officials/audit and sign attached file URLs through the storage SDK (`bpj-documents`, 60-second recommended expiry). Staff may not mutate tables directly. Audit is server-created and append-only to clients. Actor ids/names come from the active session, never browser adminInfo. Completed/rejected submissions are immutable. getAllSubmissions currently returns all rows for staff; frontend filters locally. Plan pagination before large-volume use. `bpj_dashboard()` returns counts under data.

## Retention and operational cleanup

Configure an operator-only scheduled cleanup (not a public action): enumerate objects under `pending/` that have no reference in submissions.files, are older than **24 hours**, and are not associated with any unexpired capability. Delete via service-role Storage API (not SQL deletion from storage.objects), then delete expired/consumed capability rows under your retention policy. This 24-hour quarantine exceeds Supabase signed upload URL validity (currently two hours) and prevents delete/reupload races. Keep capability records for at least that quarantine. Submission files also use pending paths; never delete solely by path prefix. No cleanup scheduler is deployed by this change.

Review storage metadata validation behavior on your Supabase version (size/mimetype fields); mismatches fail closed. MIME allowlisting is not malware scanning or file-content validation. Before staff open citizen uploads, configure a malware scanning/quarantine workflow appropriate to your risk policy. Enforce data-retention/access-review policies for NIK and applicant data; do not log request bodies or capabilities.

## Checks

`node --test supabase/tests/security.test.mjs` performs static boundary assertions; it is **not** a SQL execution or end-to-end security proof. No local PostgreSQL/Deno/Supabase executable was available during authoring. Before production, run the SQL in a staging project and test: anon table denial; ordinary Auth user denial; metadata role spoof denial; inactive staff denial; petugas approval denial; admin-only management; duplicate completion race; terminal mutation denial; empty rejection reason denial; mismatched NIK tracking denial; upload replay/wrong-size/wrong-type denial; wrong Origin; oversized body; spoofed forwarding headers; rate threshold; and signed attached-document access. Verify migrations and Edge type checking using the supported Supabase toolchain.
